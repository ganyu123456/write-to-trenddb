# 关于平台数据主题融合需求说明

## 背景

### 当前平台能力

云边协同平台（17-cloud-edge）已具备「数据通道」管理能力：

- **`cedeployedappmst`（数据通道）**：管理已部署的 MQTT Broker 应用（如 EMQX），`yml_sht` 存储完整 Helm values YAML，`deployedconfigjson_sht` 存储 paramSchema 表单填写的结构化配置
- **`cetopicmst`（主题管理）**：管理每个数据通道下的 MQTT 主题，包含主题路径（`topicpath_sht`）、传输方向（`transdirection_typ`）、QoS（`qos_typ`），通过 `broker_no` 关联到数据通道
- **已有 API**：`GET /cloudedge/mqtt/topic/list?brokerNo=xxx`

### 现有边缘应用

| 应用 | 语言 | MQTT 方向 | 当前 MQTT 配置路径 |
|------|------|-----------|-------------------|
| write-to-trenddb | C# (.NET 10) | 纯订阅 | `appSettings.Mqtt.*` |
| mqtt-iot-mapper | Go 1.22 | 订阅 status + 发布 cmd | Device CRD `spec.protocol.configData` |
| rule-engine | Go 1.22 | 订阅（源）+ 发布（每规则目标） | `engineConfig.source.*` + `rules[].target.*` |
| write-to-kafka | Go 1.23 | 纯订阅 | 环境变量 `MQTT__*` + `PIPELINES` JSON |

### 问题

1. **配置结构不统一**：四个应用四种 MQTT 配置风格，平台无法统一匹配
2. **部署时手动填写**：用户在部署向导中逐一输入 Broker、Port、Username、Password、Topics，平台已有的数据通道配置不能复用
3. **无法追溯**：平台无法回答"哪些应用消费了数据通道 X 的哪些主题"
4. **容易出错**：手动填写的主题名可能与平台配置不一致

### 目标

1. 定义**统一的 MQTT 标准配置结构**，四个应用全部按此规范改造 values.yaml
2. 数据通道通过 paramSchema 的 `provides` 声明对外暴露能力，消费应用通过 `dataChannelSelector` 发现并绑定
3. 平台增加 `ceapptopiclnk` 绑定表，实现完整数据血缘追溯

---

## 设计方案

### 核心思路：提供方声明能力 → 平台注册 → 消费方发现绑定

```
数据通道（EMQX）                         write-to-trenddb（消费方）
  paramSchema:                             paramSchema:
    provides:                                type: dataChannelSelector
      type: mqttBroker
      fields:                                  ↓ 平台查询 provides.type = mqttBroker
        broker:  emqx.xxx.bind                   找到 EMQX → 读取 deployedconfigjson_sht
        port:    emqx.xxx.port              ↓
        username: emqx.xxx.username         写入消费方的 mqtt.broker / mqtt.port / ...
        password: emqx.xxx.password         同时写入 ceapptopiclnk 绑定记录
```

- 数据通道本身仍是普通 Helm 应用，不特殊化，不增加专属数据库列
- 换 Broker（EMQX → Mosquitto → NanoMQ）只需换一份 paramSchema，平台零改动
- 所有结构化连接信息存在已有的 `deployedconfigjson_sht` 字段里

## MQTT 标准配置规范

### 顶层 mqtt 字段

所有边缘应用的 `values.yaml` 在顶层声明 `mqtt` 字段：

```yaml
mqtt:
  broker: ""        # Broker 地址（如 "192.168.122.231"）
  port: 1884        # Broker 端口
  clientId: ""      # MQTT Client ID，同一 Broker 下不可重复
  username: ""      # 认证用户名（无认证时为空）
  password: ""      # 认证密码（无认证时为空）
  qos: 1            # 默认 QoS（0 / 1 / 2）
  topics: []        # 订阅/发布的主题列表
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `broker` | string | 是 | Broker 地址 |
| `port` | int | 是 | Broker 端口 |
| `clientId` | string | 是 | MQTT Client ID |
| `username` | string | 否 | 认证用户名 |
| `password` | string | 否 | 认证密码 |
| `qos` | int | 否 | 默认 QoS，默认 1 |
| `topics` | string[] | 否 | MQTT 主题列表 |

### 多连接场景：connections 子字段

需要同时连接多个不同 Broker 时（如 rule-engine），在 `mqtt` 下增加 `connections`：

```yaml
mqtt:
  broker: "192.168.122.231"
  port: 1884
  clientId: "rule-engine"
  username: "system"
  password: "****"
  qos: 1
  topics:
    - "device/sis/data"

  connections:
    cloudTarget:
      broker: "10.0.0.1"
      port: 1883
      clientId: "rule-engine-cloud"
      username: "cloud-user"
      password: "****"
      qos: 1
      topics:
        - "cloud/sensors/batch"
```

- `mqtt.*` 为默认连接
- `mqtt.connections.<name>` 为命名连接，结构与默认连接一致
- 命名连接的 `broker` 为空时，回退到默认连接的 `broker`

## 一、平台侧改造内容

### 1.1 paramSchema 协议扩展：provides 声明

数据通道应用的 paramSchema 中新增 `provides` 声明，告诉平台"我对外暴露什么能力"：

```json
{
  "provides": {
    "type": "mqttBroker",
    "label": "MQTT Broker 连接",
    "fields": {
      "broker":   { "yamlPath": "emqx.listeners.tcp.default.bind", "label": "Broker 地址" },
      "port":     { "yamlPath": "emqx.listeners.tcp.default.port", "label": "Broker 端口" },
      "username1": { "yamlPath": "emqx.auth.username[1].username",  "label": "用户名" },
      "password1": { "yamlPath": "emqx.auth.username[0].password",  "label": "密码" }
    }
  },
  "groups": [ /* 正常的部署表单字段 */ ]
}
```

**provides 字段说明：**

| 属性 | 类型 | 说明 |
|------|------|------|
| `type` | string | 能力类型标识。`"mqttBroker"` 为 MQTT Broker 连接能力 |
| `label` | string | 能力显示名称 |
| `fields.<key>` | object | 能力包含的字段，每个字段指定 `yamlPath`（在 values.yaml 中的路径）和 `label` |

**平台处理逻辑（数据通道部署时）**：

1. paramSchema 表单正常渲染，用户填写 Broker 地址、端口、用户名、密码
2. 保存时，将 `provides.fields` 声明的字段值**同时**写入 `deployedconfigjson_sht`（结构化 JSON）和 `yml_sht`（Helm values YAML）
3. 在内部注册：`app_no=X provides type=mqttBroker`

**数据通道与主题的关联**：

数据通道部署后，用户在平台「数据通道管理 → 主题管理」tab 下添加该通道的 MQTT 主题。每条主题记录（`cetopicmst`）的 `broker_no` 指向数据通道的 `app_no`，形成外键关联。这是已有功能，无需改造。

### 1.2 paramSchema 协议扩展：dataChannelSelector 控件

消费应用的 paramSchema 中新增控件类型，告诉平台"我需要绑定一个 mqttBroker"：

```json
{
  "key": "dataChannel",
  "label": "数据通道",
  "type": "dataChannelSelector",
  "required": true,
  "dataSource": "platform.dataChannel",
  "topicDirection": "UP",
  "mqttRole": "cloudTarget",
  "description": "选择平台已配置的数据通道"
}
```

| 属性 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `type` | string | 是 | `"dataChannelSelector"` |
| `dataSource` | string | 是 | `"platform.dataChannel"` |
| `topicDirection` | string | 否 | `"UP"` / `"DOWN"` / `"BOTH"`，默认 `"BOTH"` |
| `mqttRole` | string | 否 | 多连接场景下的连接名。不声明写入 `mqtt.*`；声明写入 `mqtt.connections.<role>.*` |

**平台处理逻辑（消费应用部署时——两步查询）：**

```
dataChannelSelector 内部执行流程：

  第一步：查数据通道列表
    查询所有 provides.type = "mqttBroker" 的已部署应用
    → 从各应用的 deployedconfigjson_sht 读取 broker/port/username
    → 渲染下拉选项：[EMQX-产线A (192.168.122.231:1884), EMQX-云端 (10.0.0.1:1883), ...]

  第二步：用户选择通道后，查主题列表
    GET /cloudedge/mqtt/topic/list?brokerNo=<所选通道的app_no>
    → cetopicmst 通过 broker_no 关联到数据通道
    → 按 topicDirection 过滤方向
    → 渲染多选框：[device/sis/data, device/sis/alarm, ...]

  第三步：用户勾选主题后，写入 values.yaml
    mqtt.broker   ← deployedconfigjson_sht.broker
    mqtt.port     ← deployedconfigjson_sht.port
    mqtt.username ← deployedconfigjson_sht.username
    mqtt.password ← deployedconfigjson_sht.password
    mqtt.topics   ← 用户勾选的主题列表

  第四步：写入绑定记录
    ceapptopiclnk ← (app_no, channel_no, topic_no, SUBSCRIBE)
```

两条数据链路各司其职：

```
provides → deployedconfigjson_sht  ← 数据通道的 Broker 连接信息（host/port/username）
cetopicmst.broker_no               ← 数据通道的主题列表（通过外键关联）
```

dataChannelSelector 把两条线合并成一个操作——用户看到的是一个选择器，平台内部自动查两个数据源。

### 1.5 新增表：应用-主题绑定表（ceapptopiclnk）

```sql
create table ceapptopiclnk
(
    link_no      numeric(22) not null
        constraint ceapptopiclnk_pk primary key,
    app_no       numeric(22),           -- FK → cedeployedappmst（消费应用）
    channel_no   numeric(22),           -- FK → cedeployedappmst（数据通道）
    topic_no     numeric(22),           -- FK → cetopicmst（主题）
    binding_type varchar(20),           -- SUBSCRIBE / PUBLISH
    project_no   numeric(22),
    org_no       numeric(22),
    valid_sta    varchar(2),
    fstusr_id    numeric(50),
    lstusr_id    numeric(50),
    fstusr_dtm   timestamp(6),
    lstusr_dtm   timestamp(6)
);

comment on table ceapptopiclnk is '应用-主题绑定关系表';
comment on column ceapptopiclnk.app_no is '消费应用主键';
comment on column ceapptopiclnk.channel_no is '数据通道应用主键';
comment on column ceapptopiclnk.topic_no is '主题主键';
comment on column ceapptopiclnk.binding_type is '绑定类型：SUBSCRIBE-订阅 PUBLISH-发布';

create index idx_ceapptopiclnk_app_no on ceapptopiclnk(app_no);
create index idx_ceapptopiclnk_channel_no on ceapptopiclnk(channel_no);
create index idx_ceapptopiclnk_topic_no on ceapptopiclnk(topic_no);
```

**支持的查询：**

```sql
-- 某主题被哪些应用订阅？
SELECT a.app_nam, l.binding_type
FROM ceapptopiclnk l
JOIN cedeployedappmst a ON a.app_no = l.app_no
WHERE l.topic_no = :topicNo;

-- 某应用消费/发布了哪些主题？
SELECT t.topicpath_sht, t.transdirection_typ, l.binding_type
FROM ceapptopiclnk l
JOIN cetopicmst t ON t.topic_no = l.topic_no
WHERE l.app_no = :appNo;

-- 数据通道 X 的完整数据流向
SELECT
    t.topicpath_sht AS topic,
    pub.app_nam AS publisher,
    sub.app_nam AS subscriber
FROM cetopicmst t
LEFT JOIN ceapptopiclnk pub ON pub.topic_no = t.topic_no AND pub.binding_type = 'PUBLISH'
LEFT JOIN cedeployedappmst pub_app ON pub_app.app_no = pub.app_no
LEFT JOIN ceapptopiclnk sub ON sub.topic_no = t.topic_no AND sub.binding_type = 'SUBSCRIBE'
LEFT JOIN cedeployedappmst sub_app ON sub_app.app_no = sub.app_no
WHERE t.broker_no = :channelNo;
```

| 后端 API | `GET /dataflow/query` | 数据流向查询 |

### 1.7 数据主题表（cetopicmst）建议新增字段

| 字段名 | 类型 | 说明 | 优先级 |
|--------|------|------|--------|
| `topic_type` | varchar(20) | `STATIC`（固定）/ `TEMPLATE`（模板）/ `WILDCARD`（通配符） | P1——mqtt-iot-mapper 的动态主题 |
| `topic_pattern` | varchar(255) | 人可读模板：`device/{deviceId}/status` | P1 |
| `payload_format` | varchar(20) | Payload 格式：`JSON` / `PROTOBUF` / `TEXT` | P2——规则编辑器字段补全 |
| `payload_schema` | text | JSON Schema 或消息字段描述 | P2 |

**三种 topic_type：**

| topic_type | topicpath_sht | topic_pattern | 场景 |
|------------|--------------|---------------|------|
| `STATIC` | `device/sis/data` | — | 固定传感器主题 |
| `TEMPLATE` | `device/+/status` | `device/{deviceId}/status` | mqtt-iot-mapper 动态主题 |
| `WILDCARD` | `sensors/#` | — | rule-engine 通配符订阅 |

| write-to-trenddb | `Mqtt.*` → `mqtt.*` | 映射 `mqtt.*` → `Mqtt.*` | 不改 | 1 个 dataChannelSelector + ClientId |
| rule-engine | `engineConfig.source.*` → `mqtt.*` + `connections.cloudTarget` | 映射 `mqtt.*` → `engineConfig.source.*` | 不改 | 2 个 dataChannelSelector |
| write-to-kafka | 新增 `mqtt.*` | 新增 mqtt JSON 文件渲染 | 增加回退读取 | 1 个 dataChannelSelector + ClientId |
| mqtt-iot-mapper | 新增 `mqtt.*` | 新增 mqtt JSON 文件渲染 | 增加回退读取 | 1 个可选 dataChannelSelector |

### 2.6 数据通道应用（EMQX）改造

数据通道应用的 paramSchema 增加 `provides` 声明：

```json
{
  "provides": {
    "type": "mqttBroker",
    "label": "MQTT Broker 连接",
    "fields": {
      "broker":   { "yamlPath": "emqx.listeners.tcp.default.bind", "label": "Broker 地址" },
      "port":     { "yamlPath": "emqx.listeners.tcp.default.port", "label": "Broker 端口" },
      "username": { "yamlPath": "emqx.auth.username[0].username",  "label": "用户名" },
      "password": { "yamlPath": "emqx.auth.username[0].password",  "label": "密码" }
    }
  },
  "groups": [
    {
      "groupKey": "connection",
      "label": "连接配置",
      "fields": [
        { "key": "broker", "label": "Broker 地址", "type": "string", "required": true },
        { "key": "port",   "label": "端口", "type": "number", "required": true },
        { "key": "username", "label": "用户名", "type": "string" },
        { "key": "password", "label": "密码", "type": "password" }
      ]
    }
  ]
}
```

如果换成 Mosquitto，只需更新 `provides.fields` 中的 `yamlPath`，其他应用完全无感。

### 2.7 四类 MQTT 模式对照

**模式 1：纯订阅（write-to-trenddb、write-to-kafka）**

```yaml
mqtt:
  broker: <源 Broker>
  topics: [<订阅主题列表>]

dataChannelSelector × 1（默认模式）
```

**模式 2：订阅 + 发布（rule-engine）**

```yaml
mqtt:
  broker: <源 Broker>
  topics: [<输入主题列表>]
  connections:
    cloudTarget:
      broker: <目标 Broker>
      topics: [<输出主题列表>]

dataChannelSelector × 2（默认 + mqttRole="cloudTarget"）
```

**模式 3：Device CRD 驱动（mqtt-iot-mapper）**

```yaml
mqtt:
  broker: <回退 Broker>
  topics: []

dataChannelSelector × 1（required: false）
+ 平台内部联动：设备管理读取数据通道 → 写入 Device CRD
```

## 方案优势

**数据通道不特殊化**：数据通道仍是普通 Helm 应用，通过 `provides` 声明对外暴露能力。换成任何 Broker 只需更新 paramSchema，平台后端零改动。

**配置标准化**：四个应用统一 `mqtt.*` 结构。dataChannelSelector 写入固定路径，无需 yamlMappings。

**数据一致性**：Broker 和 Topic 统一由平台维护，杜绝手动输入导致的漂移和拼写错误。

**数据血缘可追溯**：通过 `ceapptopiclnk` 绑定表 + `deployedconfigjson_sht` 结构化配置，平台可回答：谁提供了数据通道、谁消费了哪些主题、数据通道 X 的完整流向链路。

**行业对齐**：符合 ISA-95 Unified Namespace 理念——提供方声明能力，消费方发现绑定，平台治理层居中调度。与 EMQX UNS Governance（Broker 层主题校验）形成上下两层互补。
